# ACS release assistant design

Status: version-one behavioral design reviewed; rounds 1–15 recorded. The behavioral sections below are authoritative; decision history records earlier choices, including superseded ones.

## Purpose and application structure

1. Continuously monitor preparation of a specified ACS patch release and help the user decide what to do next. Nothing-left-to-do is a current status, not a reason to stop monitoring.
2. Version one covers preparation before ACS RC.0, component release-tag and PR builds, and read-only availability checks for ACS RC.0 images. Creating ACS RC.0 and retrying its builds are deferred.
3. The tool is advisory. It must not gate the external release process or force new merges, tags, or PRs. It enforces permission rules on its own writes.
4. Application and design live in ~/code/release-assistant. Import the existing github.com/vikin91/konflux-retest library from ~/code/konflux-retest, keeping that CLI usable.
5. Use one Go executable with separate backend and Go HTML-rendering packages. Small embedded browser JavaScript is allowed; no JavaScript/TypeScript rendering engine. Serve a local browser UI.
6. Record decisions during the session. The tool must start and rediscover actual release state with an empty database. Lost counters after restart are acceptable. A database is justified only as an optimization for performance or external request volume, not as a prerequisite or source of release truth. Use in-memory working state for version one and record actions/decisions in a log file, not a database. The log is not required to reconstruct state. Never persist credentials.
7. One ACS release per running instance. Users may run several instances for parallel releases. Show the ACS release prominently in the page and browser tab title. No cross-instance locks, shared retry counters, or coordination in version one; avoiding overlapping targets is the user’s responsibility. Future multi-release support is deferred. Ports remain configurable implementation details.

## Discovery and continuous operation

1. Accept an ACS patch version, component release branches/streams, and optional pinning PR number through either CLI parameters or browser configuration. Both entry paths are supported. No automatic guessing of component branches is required. Users supply component branches/major.minor streams through CLI parameters or the UI; automatic mapping is not required. A configurable port supports parallel instances.
2. Fact, Collector, and Scanner progress independently; Scanner applies only to ACS 4.x. ACS pinning is their first shared dependency.
3. Discover repository state even when the application starts late in the release: existing tags, relevant merge history, existing pinning PRs, and already completed builds. Use merge history internally to establish tag coverage. Show only open PRs in PR selection; startup must not ask the user to include or exclude historical merged PRs. Do not force repeated work.
4. A new ACS patch version has its own selection context. If the previous patch is published and no PRs remain to merge, advise that the next patch probably is not needed. This is not a prohibition or proof that no release-worthy changes exist.
5. Use one executable and one command. Closing/reloading the browser does not stop monitoring; reopen it to reconnect. Full server restarts regenerate questions from current state and reset RW permissions off. Version one may lose session choices and counters and ask again; it must discover completed external work instead of repeating it.

## PR selection and monitoring

1. Show only open PRs targeting the configured release branches in PR selection. This applies to ACS and component repositories. Merged and closed PRs have no inclusion controls or selection rows.
2. For each visible PR, provide three immediate actions: Included, Excluded, and Ignore & hide. Show the active inclusion choice. Keep RW allowed as a separate checkbox that saves when changed, without a separate save button. Inclusion records the intent to wait for that open PR's changes in this release; it does not authorize writes or merges. An initial undecided state remains visible until the user chooses an action.
3. Undecided is a distinct state; read-only monitoring is allowed. Once the user confirms the intended open-PR selection for this session, undecided open PRs do not hold up advisory readiness. Keep them visible so the user can reconsider the release scope.
4. Ignore is a separate action: the user considers the open PR irrelevant for this release. Hide it and stop reading its details, checks, and logs. Repository-wide discovery may still return it. Do not write to ignored targets.
5. Clearing Included does not imply Ignore; monitoring may continue.
6. When an observed PR merges, remove it from the selection list. Preserve any intent recorded while it was open internally, so a selected component PR still requires a tag covering its merge. Do not ask for another inclusion decision after merge or show historical merged PRs as actionable work.
7. Component tag selection determines which merged component changes ship. Choosing a tag includes all changes contained in its resolved commit, including changes from PRs that were excluded, ignored, or undecided while open. PR selection cannot remove changes from a chosen tag. Merged ACS PRs already belong to their target ACS branch.
8. Never merge PRs or enable automerge. Observe user merges and existing automerge.
9. Limit the Retry proposals and Exact comment offers views to currently accepted component tags, PRs explicitly marked Included, and the supplied ACS pinning PR while open on the configured branch. Supplying the pinning PR number selects it for monitoring and retry display without another inclusion action. Show its controls in pinning details instead of a duplicate PR-selection row. Hide proposals and offers for excluded, undecided, ignored, merged, or closed PRs and for unaccepted or superseded tags. Preserve partial and unknown observations for selected targets. Other non-ignored open PRs may remain in read-only monitoring and in the PR selection list; view scope does not grant or revoke write permission.

## Advisory readiness and explanations

1. Apply each Included, Excluded, or Ignore choice immediately. No session-wide PR-selection confirmation or selection gate is required. An empty selection is valid; undecided PRs remain visible and do not block readiness.
2. Recommend Ready to create ACS RC.0 only when all PRs included while open have merged into their configured target branches, confirmed component tags cover those selected component changes, required component images are available, and actual ACS release-branch pins match the confirmed versions. Preserve a selected PR's coverage requirement after merge. An open pinning PR alone does not satisfy the branch-pin condition. ACS RC.0 images describe the subsequent build stage and do not block preparation for creating RC.0.
3. Present selected component tags as small neutral status pills at the top. Do not render configuration validation or session-selection cards. Summarize actual ACS pins and the supplied pinning PR separately, with an exact PR link and words explaining each status. Green branch pins mean the actual branch uses every selected component version, not overall readiness; yellow means waiting or unable to check; red means a verified mismatch. A matching open pinning PR is yellow until merged, a known target/version mismatch or closed unmerged PR is red, and a merged PR is green only when actual branch pins match. Keep version comparisons and explanations in expandable pinning details. Failed reads must name the affected PR data or version files and the concrete cause (authentication, access, missing file, rate limit, timeout, or invalid response). Use Pending only while awaiting a result. Missing local tag choices must name the required selection. Retain successful partial values and label older values as last observed. Show failures and uncertainty behind recommendations without requiring users to expand a wall of generic status cards. Tag suitability remains visible in tag details.

4. Unknown evidence for a readiness condition leaves that condition unconfirmed. Readiness is advisory and does not prevent external release actions. Continue monitoring after readiness is reached and recompute it when selection or observed state changes.
5. Every main content section must have a fold control, including recommendations, both image phases, retry proposals, comment offers, and previous component cycles. Preserve the user’s actual open or closed choice immediately for every section and nested evidence panel across polling reloads, changing observations, and form submissions. Use stable section/repository/PR/tag identities, never list positions or selection status. Only a successful release configuration save may automatically fold its own panel; rejected configuration must remain visible. Section navigation must reopen its destination when clicked, but a retained URL fragment must not override a later close on reload. Keep permanent section navigation separate from recommended next steps. Recommendations identify outstanding actions and their missing or unknown prerequisites. Replace a generic request to resolve conditions with concrete guidance about the affected selection, component image, registry observation, or branch pins. Completed tag selection is a recorded decision, separate from coverage, build, image, and release readiness.

## Permissions and interactive mode

1. Start read-only by default. The `-enable-writes` CLI flag enables write controls for that process; the flag alone grants no target permission. Without it, grey out RW permission, confirmation-mode, and comment-send controls, explain how to restart with writes enabled, and reject grants and dispatch on the server. Read-only discovery, inclusion, tag selection, advisory review, and copyable comments remain available. Write permission is per PR or tag commit, never inferred from release inclusion.
2. On every PR head change, revoke RW permission and invalidate pending interactive approval. Preserve the inclusion decision.
3. Tag permission requires the same repository, tag name, and resolved commit.
4. Interactive mode defaults on. When on, each write requires single-use confirmation of the exact target and payload in addition to RW permission. When off, per-target RW permission permits automatic retest comments; unattended operation is intended.
5. Revocation prevents new commands from being sent after the server receives it. Already dispatched requests may complete.
6. Prefer a simple implementation without a persistent outgoing-write queue. Recheck permission immediately before dispatch. A queue is acceptable if necessary; cancelling queued work was designated a stretch goal. Never let an old interactive approval override revoked permission.
7. Reset automatic write grants off after server restart. Later agreement allows session choices and counters to be lost; preserving inclusion decisions is no longer required for version one. Default interactive mode remains on.
8. Without write authorization, present retry comments for copy/paste. Changing or removing the supplied pinning PR revokes its RW grant and pending approval. A changed PR target branch also revokes permission, including when discovered during dispatch revalidation.
9. Version-one writes are retest comments. Add label writes only if required by an applicable manual step; no such requirement has been identified for the currently scoped monitoring/retest work. No application-driven merges, pushes, release triggers, or pinning PR creation.
10. A PR label named no-release-assistant overrides all local write grants. Continue read-only monitoring and show a visible write-disabled indicator. Detecting it clears local RW permission; removing it does not restore permission. The user must explicitly grant RW again. Never remove the label automatically.

## Component release cycles

1. Discover existing tags and open PRs on the configured component release branch. Offer inclusion decisions only for open PRs. Retain relevant merge history internally when needed for tag ancestry and coverage checks. A tag belongs to the branch when its resolved commit is the branch tip or an ancestor of that tip; matching the version stream alone is insufficient. Unknown branch ancestry leaves tag eligibility unconfirmed.
2. Once selected PRs have merged, provide repository-appropriate commands or release documentation for the user when another component release is needed.
3. A suitable existing tag is valid. If the tag is the branch tip and no open PRs are selected, use it without auditing its historical contents PR by PR. If the branch has advanced, changes from a PR included while open still require a tag covering its merge. Other merged changes do not require a separate inclusion decision or force a tag switch. Preserve the current tag when it already covers the selected changes. A merged PR is either contained in the chosen tag or awaits a later tag containing its merge commit; choosing that later tag includes those changes automatically. Establish containment from branch history, not tag creation time.
4. Selecting an open component PR means waiting for its merge and a tag covering the resulting branch changes. When selected changes are absent from the current tag, use a suitable newer tag if one already exists; otherwise advise cutting one after the selected PRs merge. Versions may jump: after 0.3.77, 0.3.78 or a higher eligible version is acceptable. Establish coverage through branch history and merge positions, not an exhaustive content or patch-equivalence audit; unknown evidence remains visible as unknown.
5. Use Git tags, not GitHub Release objects, and compare versions using semantic version ordering, not dates. When the supplied ACS pinning PR is merged into the configured release branch, initialize untouched component tag selections from its version files at the merge commit. Resolve each version to a final Git tag in the configured stream with verified branch ancestry and commit identity; missing or uncertain evidence leaves that component unselected. Otherwise propose the highest eligible tag and ask the user to confirm. Preserve manual selections and never restore a selection invalidated by a changed tag identity from these defaults. Default selections grant no write permission. Keep the confirmed tag in session state and work only on that tag. Newer tags generate switch proposals, never silent replacement. Separate proposal generation from decision recording for future automated decisions. Constrain selection to the applicable component major.minor stream; new tag proposals use the highest eligible patch version. Example: ACS 5.0.1 using Collector 3.25.x selects the highest patch in 3.25, never 3.26. Final-tag proposals exclude prereleases, per the accepted round-7 answer.
6. Track chosen tag builds and image existence. Keep previous observations and decisions when another release cycle starts. Once all component tags are selected, show a summary naming each component and version without changing whether the section is open. Show Selected on the current tag and offer Change tag… for alternatives, without another confirmation button for the current tag. Use an explicit switch action for a different tag; a newly available tag never changes the recorded choice automatically. Put raw SHAs and merge comparisons under Evidence, and summarize coverage for the selected scope in the main card. Tag RW permission uses the same immediate-save checkbox as PR permission.
7. If another component PR is included after pinning, immediately reassess whether the pinned tag contains its changes. Mark the pins outdated when those changes are absent; do not wait for a newer tag to appear. Preserve valid pins when the changes are already present. If containment cannot be established, show pin suitability as unknown. Compare the actual release-branch pins and any supplied pinning PR separately so an open PR that already supplies the needed versions is not reported as needing another update.

## Image and check readiness

1. Before recommending an ACS pin update, verify that both the CI and Konflux images for the chosen Fact, Collector, and applicable Scanner versions exist. These are the component release images consumed by ACS CI; the pinning PR's builds depend on them. A successful build status alone does not substitute for image existence. ACS pinning-PR builds are monitored after the PR exists. Also check ACS RC.0 image availability read-only as a separately labelled later build stage using saved naming patterns verified from the release workflow and build definitions. Do not introduce an ACS build retry or write path.
2. Trust konflux-retest as the authority for Konflux job eligibility, sequencing, and prerequisites on both PRs and tags. Never filter out its retry suggestions merely because GitHub does not mark that job Required. Optional prerequisites may be necessary for required jobs. Fix incorrect dependency knowledge in the library, not with competing rules in this application. GitHub Required checks remain useful for PR status display; unrelated optional checks need not be analyzed. For tags, use the library’s knowledge of the builds needed to produce all images. This supersedes the required-only filtering proposal from round 6.
3. Do not introduce a generic user check-waiver mechanism.
4. Do not add exhaustive architecture or attestation verification for release tracking; rely on Konflux checks. Existing retry-library input validation is separate and is not implicitly removed.
5. Report Conforma errors as a separate optional advisory even when the scenario is not required or a prerequisite. Provide an evidence link and a single Mark as reviewed button. Reviewing records a session-local flag and an action-log entry; it does not change check results, retry eligibility, write permissions, or release readiness. Keep the finding and evidence visible with a Reviewed for this session status and a Mark as unreviewed button. Explain these effects beside the advisories. Review state resets on restart. No automatic Conforma retries or release blocking. Log analysis can be inaccurate; do not declare errors harmless automatically.
6. Unknown state, registry access failures, and missing observations are not evidence of success or confirmed absence.
7. Present component images and ACS RC.0 images in separate foldable sections because they belong to different release phases. Component images are prerequisites before ACS pinning; ACS RC.0 images belong after pinning and RC.0 creation and start collapsed. Within each section, list expected images in a numbered list, naming the component, CI or Konflux family, variant, exact image tag/reference, and Available, Not found, or Unable to check status. Explain failed registry requests and missing tag selections in plain language. Link to the exact registry tag; a saved immutable source link documents pattern provenance and is not a runtime prerequisite. Omit generic GitHub source links. Preserve successful partial observations and visibly mark last-known results as unverified when a refresh fails. Missing or invalid selected tags leave their images unknown, without invalidating independently checked rows.
8. Readiness remains advisory; failed checks and unresolved decisions remain visible without preventing external release actions.

## ACS pinning and PR monitoring

1. When applicable component versions and both their CI and Konflux images are ready, provide copyable commands for the user to create or update the ACS pinning PR. If images are missing or their availability is unknown, explain which images the pin update is waiting for. Do not publish branches or create PRs on the user's behalf.
2. Accept a manually supplied pinning PR number and keep it for the session; no restart persistence required. Optional discovery may inspect changes to any applicable version-pin files, but no minimum count of changed files is assumed. Prefer manual input if discovery adds complexity. Inspect actual release-branch pins too so already completed work can be recognized.
3. If an existing pinning PR is open, suggest updating it when components change; if already merged, suggest a new pinning PR.
4. Generated commands must not use git-spice. Assume a user-provided cdrox alias changes into the intended StackRox checkout. Commands are suggestions for copying/editing; the user may execute their own workflow instead. Follow the explicitly selected release branch as the pinning target; final command content remains to be settled.
5. Show open ACS release-branch PRs with the same inclusion and RW controls, and monitor using the retry library. Remove merged PRs from selection and read actual branch pins to recognize completed pinning work. Release actions stop before ACS RC.0; read-only RC.0 image checks and monitoring continue while the server runs.

## Existing retry project observations

1. README and go.mod describe Go 1.26.0, reusable CheckPR and CheckTag functions, and a read-only CLI. This is not a completed code audit.
2. The library generally selects retries from statuses and dependency readiness; it does not establish that a failed job is a flake.
3. Partial results may accompany errors. The application must preserve uncertainty for affected jobs.
4. The library skips merged/closed PRs. Track tag containment and the merge coverage required by PRs included while open internally; this evidence does not create historical PR selection tasks.
5. CI retry means posting a retest comment to request another CI execution; read-only API request retries are a separate policy. Apply the additional dispatch rules below to existing library suggestions.

8. Monitor the configured open pinning PR’s current-head GitHub checks, library retry suggestions, and reported Konflux build images separately from component prerequisites and ACS RC.0 images. Obtain literal image URL/digest outputs only from identity-verified PipelineRuns or their archived records; verify registry availability by the reported immutable digest. Missing outputs and failed reads remain unknown. Do not derive PR tags from version/branch assumptions, treat build success as registry proof, or change retry eligibility from output-image availability. Show CI check statuses without claiming CI output-image availability when no verified reference is available. Stop PR retries after it merges or closes. Keep per-image text focused on the image and its availability; phase labels belong in section headings.

## Retest dispatch rules

1. Normally post a retest comment only when the relevant pipeline is positively known to be finished unsuccessfully and konflux-retest identifies it as needing a retry for release progress. The narrow no-observed-run case is described under Final scope decisions; it requires explicit library support and is never inferred from a timeout alone. Failure, cancellation, and timeout are eligible; do not exclude cancellations based on guessed human intent. Never post while that job is running, queued, pending, or has uncertain state. Long queues may last hours and are not a reason to post another comment.
2. Use fresh konflux-retest results to decide whether a job can be retried, both during normal operation and after restart. The library interprets GitHub checks and any additional evidence it needs. Pending, queued, and running jobs must not produce another retest comment. For other states, send only a retry the library recommends, subject to application permission and rate limits. Fix missing state handling in the library rather than adding a competing retry planner or comment-history reconciliation system here.
3. Enforce a minimum one-minute gap between outgoing comments to a given target across its jobs. This is a burst limit, not a schedule. Re-evaluate the library recommendation after the gap expires; do not accumulate and replay stale retry requests. Show when a retry is waiting for the rate limit, and request interactive confirmation only when it can be dispatched without queuing the approval.
4. Count distinct consecutive unsuccessful eligible runs (including cancellation and timeout) for the same job + target + commit, not comments. Success or a new commit resets the count. Default threshold: ten consecutive failures, configurable. At threshold, display a persistent warning.
5. After the threshold, slow that job to at most one retest comment per hour, configurable. Other jobs retain the ordinary target-wide minimum gap. All failure-evidence and permission requirements still apply.
6. Log comment delivery as sent, failed, or uncertain. Do not immediately replay a write after a transport error. At the next eligible evaluation, refresh the library result and apply the same permission and rate-limit checks. Do not require a separate user recovery decision or persistent request history after restart. Retry suppression relies on the check state interpreted by the library; the application does not independently guarantee that a previous comment has already produced a visible run.
7. Preserve current permission and commit checks at dispatch, including no-release-assistant label enforcement. Unknown current authorization or run state must withhold writes.
8. Inform the user when an interactive proposal has become stale. Prefer a simple revalidation before sending rather than an elaborate live invalidation system. If target, permissions, opt-out label, or relevant pipeline state no longer supports the approved action, do not send it and show updated information. Rich change notifications are optional if costly. Rejection suppresses the proposal for the specific run, with manual reconsideration available; this was included in the accepted round-7 proposal.

## Manual label review

1. The main release manual limits creation of backport release-X.Y labels to normal releases and explicitly skips that setup for patches.
2. The related backport guide uses labels to request backport PR creation. That is a separate workflow from monitoring existing PRs in this design.
3. No label writes are currently needed for scoped version-one retest comments. no-release-assistant is a read-only opt-out signal, not a label the assistant must create or apply.
4. Sources: https://redhat.atlassian.net/wiki/spaces/StackRox/pages/309339008 and https://redhat.atlassian.net/wiki/spaces/StackRox/pages/309335022 .

## Authentication

1. Credentials must come from environment variables or an existing user-authenticated tool/session, such as oc login or gh authentication. Do not introduce an application credential store or save credentials in SQLite, exports, or logs.
2. User handles authentication. Reusing existing retry CLI credential discovery is acceptable only within this constraint. Exact environment-variable precedence and reload behavior remain to be specified.

## Polling and outages

1. Refresh active checks approximately every minute and discover PRs/tags approximately every five minutes. Both intervals must be configurable.
2. On access errors, use exponential backoff. The earlier proposed five-minute cap is acceptable as a configurable default.
3. Keep last observed state with observation time. Unknown or inaccessible current state must withhold writes requiring verification. Recover automatically when access returns.
4. Empty local state is supported; no persisted counters or cached observations are required for startup correctness.

## Action log

1. Write decisions and actions to a local log file, not a database. Include observation/action time, release identity, target identity and commit, decision, proposed/sent comment, result or uncertainty, and user/system origin as applicable.
2. Log permission changes, inclusion/ignore choices, tag selections, interactive approvals/rejections, retest dispatch/results, and important state transitions. Do not include credentials.
3. Prefer append-only records and configurable log location. Format and rotation are implementation choices; avoid logging every unchanged poll.
4. Logs need not be replayed on startup; a fresh instance rediscovers state and asks for choices again.

## Final scope decisions

1. Users provide component release branches/streams through CLI or UI. Do not require automatic inference or hard-coded ACS-to-component mappings.
2. GitHub Actions and Prow/OSCI status, image availability, and links are read-only observations in version one. Automatic GHA/Prow retests may be added later; version-one automatic retest writes remain limited to comments supplied by konflux-retest.
3. If a required build has no observed run, display Required build not observed and keep discovering. Do not invent a retry comment. Only an explicit library-supported suggestion for that situation may be considered, subject to authorization, freshness, and rate limits. The user may investigate or trigger externally.
4. Overall readiness must remain explainable through the underlying statuses. Component tag suitability follows configured branch history and selected PRs. Component CI and Konflux images must exist before recommending pinning. Konflux retry eligibility belongs to konflux-retest. Implementation must preserve these authority boundaries and avoid adding features solely to resolve technical details.

## Implementation details to resolve during implementation, not new feature scope

1. Use GitHub read APIs for release discovery and the existing retry library for Konflux retry eligibility. Keep library suggestions separate from application permission, freshness, and rate-limit checks. Any additional Konflux evidence needed to decide retry eligibility belongs in the library.
2. The retry library must distinguish tagged versus branch-triggered runs accurately. Failure to establish identity yields unknown, not permission to dispatch; address gaps in the library rather than duplicating that logic here.
3. Generate advisory cdrox-based pinning commands using the chosen component versions, applicable version files, and correct ACS release branch. Do not execute them. Never include unrelated local changes in suggested staging commands.
4. Configuration precedence, log format, polling jitter/backoff, and local request protection should use simple conventional implementations.
5. A frontend/backend package separation is sufficient; no separate service deployment, mandatory database, cross-instance coordinator, or complex persistent write queue.
6. Verify image names and tag suffixes from upstream source during implementation and save the patterns in the application with immutable provenance. Compute all expected image references locally from selected component versions and the ACS release version. CI uses `quay.io/rhacs-eng/<image>:<version>`; Konflux uses `quay.io/rhacs-eng/release-<image>:<version>-fast`. Scanner V2 uses scanner, scanner-db, scanner-slim, and scanner-db-slim for ACS 4.x. ACS RC.0 uses `<acs-version>-rc.0`: ACS 4.x checks main, roxctl, central-db, scanner-v4, and scanner-v4-db; ACS 5.x checks main, roxctl, and scanner-v4. The saved family patterns are verified against ACS 4.10, 4.11, and 5.0. Registry checks must not fetch Makefiles, scripts, or pipeline definitions at runtime, require a local checkout, or wait for GitHub discovery. Bind results to selected versions and release identity; source branch SHA is not image identity. Keep GitHub uncertainty as a separate readiness concern. This does not change the retry library's source validation or eligibility authority.
